## 0. 先说三件必须先说清楚的事

**一、李跳跳不是开源项目。**

这一点得先纠正，否则「参考李跳跳开源项目」这个前提是站不住的。李跳跳是闭源单机 App（约 2MB，不联网、无盈利），
网上流传的是社区逆向出来的**规则包**，没有源码。它的产品思路可以学，代码没法参考。
真正能拿来对照实现的开源同类是 GKD。

**二、李跳跳的结局直接决定了这个项目的设计边界。**

2023-08-24，李跳跳作者公告「无限期停止更新」，原因是收到某大厂律师函，援引《反不正当竞争法》第二条、
第十二条第二款第四项，主张「屏蔽、过滤广告服务」构成不正当竞争。同期「大圣净化」「一指禅」「叮小跳」
等同类工具收到同一批律师函，多数下架停运（其中一款下载量近 100 万）。

法律界对此**没有统一结论**：有律师认为这类工具非盈利、非联网，不具备「经营者」主体资格，不构成不正当竞争；
也有律师认为利用无障碍服务自动关闭他人广告，实质上妨碍了他人商业模式，构成侵权。目前没有形成生效判例共识。

**三、因此本项目的定位是「个人自用工具」，并据此设了硬边界。**

| 做 | 不做 |
|---|---|
| 本机无障碍点击 | 修改、重打包、注入任何第三方 App |
| 本地规则匹配 | 拦截、代理、篡改网络请求 |
| 离线运行 | 云端上传界面内容 |
| 个人自用 | 商业化、分发规则牟利、上架应用商店 |

代码里所有设计选择都服从这条边界 —— 比如为什么不做网络层拦截、为什么不做 Root 提权、
为什么规则必须验签，根子都在这里。

## 1. 适用安卓版本与权限要求

### 1.1 版本矩阵

| 项目 | 取值 | 理由 |
|---|---|---|
| `minSdk` | **26（Android 8.0）** | 无障碍 API 在 8.0 趋于稳定；`dispatchGesture` 从 7.0 起可用但 8.0 才稳定；低于 8.0 的存量设备已极少 |
| `targetSdk` | **35（Android 15）** | 跟随最新政策，同时把 14/15 的行为变更都在编译期暴露出来 |
| 推荐运行版本 | **Android 10 ~ 15** | 10 以上 `takeScreenshot`、多窗口、`queries` 等能力齐全 |
| 明确不支持 | Android 7.1 及以下 | `AccessibilityNodeInfo` 行为差异大，维护成本不成正比 |

GKD 的 `minSdk` 是 24（Android 7.0），比我们低一档。我们抬到 26 是为了少写一批版本兼容分支，
代价是可覆盖设备少一点 —— 对一个个人工具来说这笔交易划算。

### 1.2 各版本的关键差异与应对

| Android | API | 对本项目的实际影响 | 代码里的应对 |
|---|---|---|---|
| 8.0 | 26 | 基线 | — |
| 9 | 28 | 后台执行限制收紧 | 引导加电池白名单；不依赖后台常驻轮询 |
| 10 | 29 | 分区存储；**后台不能启动 Activity** | 规则落 `filesDir`；学习模式用**通知**而非弹窗确认 |
| 11 | 30 | 包可见性（`queries`）；新增 `takeScreenshot` | manifest 用 `<queries>` 声明；截图兜底预留 |
| 12 | 31 | 侧载应用「受限制的设置」；`PendingIntent` 必须声明 mutability | 引导用户开「允许受限制的设置」；全部 `FLAG_IMMUTABLE` |
| 13 | 33 | `POST_NOTIFICATIONS` 变运行时权限；`AccessibilityNodeInfo.recycle()` 废弃 | 运行时申请通知权限；`recycle` 只在 SDK<33 调用 |
| 14 | 34 | 前台服务必须声明类型；隐式 Intent 受限 | 全部显式 Intent；不用长时前台服务 |
| 15 | 35 | 前台服务有时长上限；强制 edge-to-edge | 设计上不依赖前台服务，天然规避 |

### 1.3 权限清单

| 权限 | 类型 | 用途 | 必需性 |
|---|---|---|---|
| `BIND_ACCESSIBILITY_SERVICE` | 服务级（manifest 声明） | 无障碍服务的准入凭证，由系统校验 | **必需** |
| 用户手动开启无障碍 | 特殊权限（设置页） | 实际授权动作，无法用代码申请 | **必需** |
| `POST_NOTIFICATIONS` | 运行时权限（13+） | 学习模式的确认通知 | 可选，不给只影响半自动模式 |
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | 普通权限 + 系统弹窗 | 引导加电池白名单 | 可选 |
| `INTERNET` / `ACCESS_NETWORK_STATE` | 普通权限 | 拉取规则订阅 | 可选，纯离线可用 |
| `QUERY_ALL_PACKAGES` | **刻意不申请** | — | 用 `<queries>` 声明 `LAUNCHER` intent 替代，避免应用商店敏感权限审查 |

关键认知：**无障碍服务不是一个「权限」，而是一种「特殊能力」**。它不在运行时权限体系里，
用户必须去「设置 → 无障碍 → 已下载的服务」手动开启，代码无法代劳，也无法检测「用户点了拒绝」
—— 只能轮询检查 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 判断当前是否开启。

还有一个国产 ROM 特有的坑：侧载安装的 App 在 Android 12+ 上会提示「受限制的设置，出于安全考虑不可用」。
需要用户到「应用信息 → 右上角 → 允许受限制的设置」里放开（小米在「高级设置」里，路径各家不同）。
这一点必须写进引导文案，否则大量用户会卡在这一步以为是 App 坏了。

## 2. 广告识别方式

### 2.1 三条路线的取舍

| 方式 | 原理 | 准确率 | 功耗 | 通用性 | 本项目定位 |
|---|---|---|---|---|---|
| **控件/节点匹配** | 读 `AccessibilityNodeInfo` 树，按文本 / viewId / 类名 / 区域匹配 | 高 | 低 | 高（覆盖 90%+） | **主线** |
| **图像识别** | 截图 + 模板匹配 / OCR | 中 | 高 | 低（模板会随版本失效） | **兜底，默认关闭** |
| **无障碍规则引擎** | 上述两者 + 状态机调度 | — | — | — | **框架层** |

结论很明确：**开屏广告场景里，节点匹配的性价比碾压图像识别**。原因在于开屏广告的「跳过」按钮
绝大多数是原生 `TextView`，无障碍树里天然带着文本；而图像识别要额外解决截图权限、模板随 App 改版失效、
以及常驻截图带来的功耗和隐私问题。

图像识别在这里的边际收益极低，所以本项目 v1 **不做**，只在架构上留位置（见 2.5）。

### 2.2 节点匹配的四个维度

代码里对应 `core/model/Selector.kt`：

```kotlin
data class Selector(
    val text: List<String>,          // 文本候选集，任一命中
    val textMode: TextMode,          // EXACT / PREFIX / CONTAINS / REGEX
    val matchDesc: Boolean,          // 是否同时匹配 contentDescription
    val viewIdSuffix: String?,       // viewId 后缀，如 "skip"
    val className: String?,          // "TextView" / "*"
    val region: Region?,             // 归一化屏幕区域
    val maxTextLength: Int,          // 文本长度上限
    val minWidthDp: Int,
    val minHeightDp: Int,
)
```

**为什么是这四个维度，而不是 GKD 那种完整 CSS 选择器？**

GKD 用了一套 CSS 式的 AST 选择器：支持父子/兄弟关系（`div > img`）、布尔表达式（`[a=1][b^='2']`）、
取反（`!(f=true)`）、甚至表达式运算（`[g.plus(1)>0]`）。表达能力最强，但解析器 + 匹配器的工程量
大概是这套扁平结构的 6~8 倍。

开屏跳过是个**极窄的场景**：目标永远是「屏幕上某个写着『跳过』的小按钮」。用「文本 + 区域 + 尺寸 +
类名」这四把锁，已经能锁定 90% 以上的情况。剩下的 10% 靠 App 专属规则（viewId）补。

> **1.1.0 起这套取舍不再 exclusive**：GKD 那套树形关系选择器已经整套搬进来了（见 6.4），
> 原生格式的扁平 `Selector` 保留，两条路径并存。
> 当年「先做窄的、留扩展位」的判断依然对 —— 正是把 `RelationSelector` 的扩展位
> 填上，才让 GKD 订阅能直接用，而不用改写引擎里任何一个已有分支。

### 2.3 文本归一化 —— 这是准确率的关键

直接 `text == "跳过"` 在实际环境下几乎必然失败。真实文案长这样：

```
跳过    跳 过    跳过广告    跳过广告 3    跳过 | 5s    跳.过    跳過    SKIP
```

`core/match/TextNormalizer.kt` 的处理链：

```
全角转半角 → 丢弃标点与空白 → 繁转简 → 转小写
```

归一化后 `"跳过广告 3s"` 变成 `"跳过广告3s"`，此时用 `PREFIX` 匹配 `"跳过"` 就通了。

三种文本模式的实测取舍：

| 模式 | 适用 | 风险 |
|---|---|---|
| `EXACT` | 文案干净的按钮 | 倒计时变体全部失效 |
| `PREFIX` | **倒计时按钮主力**（`跳过 5`） | 会误吃「跳过广告，立即领取」这类钓鱼文案 |
| `CONTAINS` | 已人工验证过的重灾 App | 误点率最高，只建议在专属规则里用 |
| `REGEX` | 复杂变体逃生口 | 性能与可读性差 |

`PREFIX` 的风险靠下一节的护栏兜住。

### 2.4 误点护栏 —— 本项目跟 GKD 思路最不一样的地方

`core/match/SafetyGuard.kt` 在点击前做五道检查：

| 护栏 | 阈值 | 拦的是什么 |
|---|---|---|
| 面积占比 | > 28%（严格模式 12%） | 整屏广告图 `ImageView` 被加上 `clickable=true`，点一下就进广告页 |
| 尺寸为零 | — | 布局未完成时的空节点 |
| `isEnabled` | 必须 true | 部分 App 的按钮 3 秒后才可点 |
| 文本黑名单 | 下载/领取/立即打开/同意/支付… | 假「跳过」，点了跳下载页或支付页 |
| 严格模式 | 必须自身可点击 | 无文本纯图按钮的盲点 |

**为什么这层比选择器精度更重要？** 因为误点的代价是不对称的：

- 漏跳 → 多看 5 秒广告，用户骂一句，下次还能跳
- 误点 → 可能直接下单、下载、跳应用商店、签到领奖，**不可撤销**

GKD 把精度责任全压在规则作者身上（选择器写得准就行）。这在一个有 1300+ 条规则、有社区审核的
生态里是合理的。但本项目规则量小、没有审核流程，所以在**运行时**再加一层保险，宁可漏跳。

护栏还带回溯记录：被拦截时也会写一条 `HitRecord`（`note = "被安全护栏拦截：面积占比 100% 超过阈值"`），
用户在「命中日志」里能直接看到「为什么这次没跳」，而不是对着屏幕猜。

### 2.5 图像识别兜底（v2 预留，v1 不实现）

设计上留了两条路径，都只在节点匹配完全失效时触发：

| 方案 | 实现 | 代价 |
|---|---|---|
| `AccessibilityService.takeScreenshot()`（API 30+） | 支持「用户教一次」：长按框选按钮区域存为模板，下次做 8×8 灰度 NCC 匹配 | 每次截图约 5~15ms，需限流到「同一 Activity 只试一次」 |
| `MediaProjection` 常驻录屏 | 可拿到全帧 | 常驻录屏通知，用户接受度极低，**不推荐** |

触发条件写死为：`节点树中右上角区域存在 ImageView，但整棵树找不到任何可用文本候选`。
满足这个条件才截一次图，且同一 Activity 生命周期内只截一次。

诚实地说：这条路径的投入产出比很差，大概率永远不会是主力。

## 3. 触发逻辑：自动与半自动

### 3.1 核心模型：把「一次开屏」建模成会话

这是整个引擎最重要的设计判断。开屏广告不是瞬间就绪的：

```
T+0ms      SplashActivity 起来，节点树里只有一个空 FrameLayout
T+300ms    广告 SDK 异步回包，插入 ImageView + 倒计时 TextView
T+500ms    「跳过 3」按钮才真正可点
```

如果只在 `WINDOW_STATE_CHANGED` 时匹配一次，**90% 的 App 都跳不过**。
所以引入 `Session`（`core/engine/Session.kt`）：

```
窗口变化
   │
   ├─ 解析规则：包名 + Activity 命中？
   │      否 → Idle，结束（不遍历节点树，零开销）
   │      是 ↓
   ├─ 冷却检查：距上次点击同规则 < actionCooldownMs？ → Idle
   ├─ 模式检查：LEARN 且未确认？ → 发确认通知，NeedsConfirm
   │
   ▼
创建 Session（记录 startedAt）
   │
   ├─ 立即尝试一次
   │     失败 → Retry(60ms)
   │              Retry(120ms)
   │                Retry(200ms)      ← 累加约 2.0s
   │                  Retry(320ms)       配合 timeout=3s
   │                    Retry(500ms)
   │                      Retry(800ms)
   │                        超时 → 销毁 Session，Exhausted
   │
   └─ 期间任何 WINDOW_CONTENT_CHANGED 都会触发一次额外尝试
          （广告按钮后出现的主要捕获手段）
```

`Decision` 把决策和执行分离，引擎不碰定时器：

```kotlin
sealed interface Decision {
    data object Idle
    data object Skipped
    data class  Retry(val afterMs: Long)
    data class  Exhausted(val reason: String)
    data class  NeedsConfirm(val rule: AppRule)
}
```

好处是引擎可以纯 JVM 跑单测（`core/src/test/`），不用 Robolectric。

### 3.2 全自动

默认模式。命中即点，用户无感。适用于规则已经稳定验证过的 App。

### 3.3 半自动（学习模式）

这是本项目对「半自动」的落地方式，跟常见的「弹窗问你要不要点」不一样。

**为什么不做「弹窗询问」？** 因为等用户看到弹窗再点，广告早就播完了，体验比不跳还差。
而且 Android 10+ 禁止后台启动 Activity，弹窗本身也做不了。

真正的半自动语义是：**每个 App 第一次遇到时问一次，确认后永久转自动**。

```
首次遇到 App X 的开屏
   │
   ├─ 不点击
   ├─ 发一条通知：「检测到「X」的开屏广告 — 启用后以后自动跳过」
   │      [以后自动跳]  [不用了]
   │
   ├─ 点「以后自动跳」→ repo.setConfirmed(ruleId) + config.setMode(pkg, AUTO)
   └─ 点「不用了」    → setConfirmed + setMode(pkg, DISABLED)
```

代码：`a11y/ConfirmNotifier.kt` + `a11y/ConfirmReceiver.kt`。用通知而不是悬浮窗，
是因为悬浮窗要 `SYSTEM_ALERT_WINDOW`，国产 ROM 申请成功率低，且用户看到「显示在其他应用上层」
基本就劝退了。通知是零额外权限的方案。

### 3.4 三档强度

| 强度 | 允许 | 典型场景 |
|---|---|---|
| `STRICT` | 只点原生可点击 + 文本精确/前缀 + 区域内 + 面积 ≤12% | 通用兜底规则（`packages: ["*"]`） |
| `NORMAL` | 允许 `dispatchGesture` 手势兜底 | 大多数 App 专属规则 |
| `AGGRESSIVE` | 允许无文本纯图按钮、放松区域限制 | 用户显式为某个顽固 App 开启 |

全局模式（AUTO / LEARN / DISABLED）+ 单 App 覆盖 + 规则自带强度，三层优先级从低到高。
代码：`a11y/AppConfigStore.kt`。

## 4. 规则配置与更新机制

### 4.1 规则格式

**只支持 GKD 格式**（1.2.0 起删掉了自研扁平 JSON 格式，见文档开头）：

| 格式 | 解析器 | 适用 |
|---|---|---|
| GKD JSON5 | 手写的 `Json5` 解析器 | GKD 社区订阅（如 `gkd.json5`） |

GKD 订阅的结构：

```json
{
  "id": "your.subscription.id",
  "name": "示例订阅",
  "version": 1,
  "minEngine": 1,
  "updatedAt": "2026-10-27",
  "rules": [
    {
      "id": "com.taobao.taobao.splash",
      "name": "淘宝 开屏",
      "packages": ["com.taobao.taobao"],
      "activities": [".*Splash.*", ".*Welcome.*"],
      "excludeActivities": [],
      "priority": 100,
      "matchDelayMs": 0,
      "timeoutMs": 3000,
      "actionCooldownMs": 1500,
      "maxTriggers": 4,
      "strength": "NORMAL",
      "note": "模板规则，需真机快照核对",
      "steps": [
        {
          "selector": {
            "text": ["跳过"],
            "textMode": "PREFIX",
            "className": "TextView",
            "region": [0.5, 0, 1, 0.2],
            "maxTextLength": 10
          },
          "action": "CLICK_NODE"
        }
      ]
    }
  ]
}
```

`steps` 是**有序**的，第一个命中的生效 —— 所以精确文本要排在前缀文本前面。

原生格式的 `steps` 里也可以直接写 GKD 选择器（用 `gkd` 字段代替 `selector`）：

```json
{ "gkd": "@[text*=\"跳过\"][text.length<10]" }
```

这样手写规则也能用上关系选择器，不必去改写成扁平结构。

### 4.2 两级来源合并

```
优先级：USER(2) > REMOTE(1)
```

| 来源 | 位置 | 作用 |
|---|---|---|
| REMOTE | `filesDir/rules/remote/<id>.json` | 订阅下发，主力来源 |


**内置规则已移除。** 早期版本在 `assets/rules/default.json` 里放了一份兜底规则集，
保证「装上不开网也能跳」；现在这条路去掉了，规则完全由用户添加的订阅决定。
代价是首次安装后规则数为 0、什么都跳不了，所以首页和订阅页都做了引导文案。

这样取舍的理由：内置规则集必须跟着 APK 发版才能更新，而开屏广告的按钮文案
和 Activity 名变化很快 —— 一份写死在内置包里、几个月不更新的规则，
实际命中率会掉到很低，反而让用户觉得「这 App 没用」。
走订阅后规则可以独立迭代。

合并键是 `rule.id`，**高优先级整体覆盖低优先级**（不是字段级 merge）。
字段级 merge 看着聪明，实际会让一条残缺的用户规则把订阅规则的关键字段冲成 null，
debug 时能让人崩溃。

### 4.3 更新流程

```
WorkManager（12h 周期 / 仅 Wi-Fi 可用时）
   │
   ├─ 1. GET {updateUrl}.version        ← 只返回版本号，几十字节
   │       remote <= local ? → UpToDate，结束（省流量）
   │
   ├─ 2. GET {updateUrl}                ← 全量 JSON，保留原始字节
   │
   ├─ 3. GET {updateUrl}.sig            ← Base64 签名
   │       缺失 / 验签失败 → 拒收，保留旧版本
   │
   ├─ 4. 解析 + 校验（minEngine / id 一致性 / 逐条规则容错）
   │
   ├─ 5. 版本回退保护：sub.version <= localVersion → 丢弃
   │
   └─ 6. 落盘 → reloadLocked() 重建索引 → 服务侧下一次事件自动用新规则
```

第 1 步的 `checkUpdateUrl` 设计是直接从 GKD 学的 —— 国内网络环境下，先拉一个几十字节的版本号，
比每次下几百 KB 全量规则的成功率和流量都好得多。

### 4.4 签名校验 —— 这是 GKD 没做、但必须做的一环

> **⚠️ 1.2.0 已整体删除。** 这一节保留的是当时的设计推演，实际落地时发现前提不成立：
> GKD 社区根本没有签名体系，强制验签等于把所有现成订阅源全部拒收。
> 现在的做法见 6.x「GKD 订阅没有签名」—— 识别为 GKD 格式直接按未验签加载，
> 在订阅列表里明确标注。下面是当时的设计，仅供追溯。

**为什么必须验签？** 因为规则文件本质上是「能替你点屏幕上任何东西的脚本」。

一个被投毒的订阅可以把规则改成：

```json
{
  "packages": ["com.android.settings", "com.tencent.mm"],
  "steps": [{ "selector": { "text": ["确认", "支付", "同意"] }, "action": "CLICK_NODE" }]
}
```

用户在支付页、权限授权页被自动点「确认」。这不是理论风险 —— 任何支持第三方订阅的自动化工具
都天然暴露这个攻击面。

> **1.2.0 已移除**：规则来源只剩 GKD 订阅，而 GKD 社区没有签名体系，
> 验签等于拒收所有现成源。以下保留为设计决策记录。

实现（`rules/RuleVerifier.kt`）：

```kotlin
Signature.getInstance("SHA256withECDSA")  // ECDSA P-256
```

**为什么不用 Ed25519？** 因为 Ed25519 要到 Android 13（API 33）JCA 才原生支持，
而 `minSdk` 是 26。用 BouncyCastle 补 Ed25519 要多打 2MB 依赖，不值。
ECDSA P-256 全版本可用，安全性对「签一个规则文件」这种场景绰绰有余。

两个容易踩的细节：

1. **验签必须基于原始字节**。不能先 parse 再重新序列化 —— 字段顺序、空格、数字格式都会变，
   字节一变签名必然对不上。所以 `RuleRepository` 落盘时存的是原始 JSON 字符串，不是解析后的对象。
2. **公钥内置，私钥只在发版机器上**。私钥进仓库 = 整个机制失效。

### 4.5 订阅管理（UI 层）

用户可以通过 URL 添加任意订阅源，并支持编辑与删除。

**数据模型分两层**，这点容易搞混：

| 类型 | 是什么 | 生命周期 |
|---|---|---|
| `Subscription` | 订阅**包本身**（从 JSON 解析出的规则集合） | 拉取成功后才有 |
| `SubscriptionEntry` | 用户的**配置**（从哪拉、要不要验签、开不开） | 用户添加时就存在 |

分开的原因：用户刚填了 URL 但拉取失败时，只有配置没有内容，
但这条记录仍然要留在列表里显示错误状态。两者用订阅 id 关联。

**三个操作的行为**：

| 操作 | 流程 |
|---|---|
| 添加 | 输入 URL → 立即拉取 → 验签 → 解析 → 落盘 → 保存配置 |
| 同步 | 版本探测（只拉几十字节）→ 版本变了才拉全量 → 落盘 |
| 删除 | 移除配置 + 删除 `filesDir/rules/remote/<id>.json` |

**两个刻意的设计**：

1. **URL 不可编辑**。订阅的身份就是 URL，改了等于换了个订阅。
   与其做「改 URL 时重新拉取 + 迁移 id」的复杂逻辑，不如让用户删了重加。
   名称、版本检查地址、验签开关、启用状态都能随时改。
2. **验签默认开启，但允许关闭**。规则本质是「能替你点屏幕的脚本」，
   被投毒可以改成「确认支付」。所以默认强制验签；自建源没有签名的场景下，
   用户可以在添加时显式关掉，UI 上有明确的风险提示。

**一个必须知道的坑**：Fragment 用 `hide/show` 切换时**不会触发 `onResume`**，
只触发 `onHiddenChanged`。第一版把刷新逻辑全放在 `onResume` 里，
结果在订阅页加完订阅切回首页，规则数还停在 10 条（实际已经是 12），
看起来完全像功能坏了。四个 Fragment 都要补：

```kotlin
override fun onHiddenChanged(hidden: Boolean) {
    super.onHiddenChanged(hidden)
    if (!hidden) refresh()
}
```

**怎么验证这个功能**：

宿主机起一个静态文件服务提供测试订阅，模拟器里用
`http://10.0.2.2:<port>/subscription.json` 添加
（`10.0.2.2` 是 Android 模拟器访问宿主机的固定地址），添加时关掉验签开关即可。

```js
// server.js —— 直接 serve 当前目录
require('http').createServer((req, res) => {
  require('fs').readFile(__dirname + req.url, (e, d) => {
    if (e) { res.writeHead(404); res.end(); return; }
    res.writeHead(200, { 'Content-Type': 'application/json' }); res.end(d);
  });
}).listen(8123, '0.0.0.0');
```

注意：输入 URL 时软键盘弹出会把对话框整体顶上去，
用 adb 做自动化测试时，必须先 `input keyevent 111` 收起键盘再按坐标点击，
否则会点到对话框外面。

### 4.6 可扩展机制小结

| 扩展点 | 做法 |
|---|---|
| 新增 App 支持 | 加一条 JSON 规则，不改代码、不发版 |
| 新增匹配维度 | 扩展 `Selector` 字段 + `NodeMatcher` 加一个分支 |
| 新增动作类型 | 扩展 `Action` 枚举 + `SplashSkipService.perform()` 加一个分支 |
| 关系选择器 | `RelationSelector` 已留扩展位，v2 实现 |
| 多订阅源 | `remote/` 目录多文件，按 id 各自合并 |
| 规则调试 | 「命中日志」页 + 规则详情对话框展示完整匹配链路 |

## 5. 无障碍服务与后台运行实现要点

### 5.1 服务配置

`a11y/src/main/res/xml/accessibility_service_config.xml`：

```xml
android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged|typeWindowsChanged"
android:accessibilityFlags="flagReportViewIds|flagRetrieveInteractiveWindows|flagIncludeNotImportantViews"
android:canRetrieveWindowContent="true"
android:canPerformGestures="true"
android:notificationTimeout="100"
```

逐个说清楚为什么：

| 配置 | 为什么 |
|---|---|
| `typeWindowStateChanged` | 主触发点，**只有它的 className 才是 Activity 全名** |
| `typeWindowContentChanged` | 应对「广告异步加载、按钮后出现」。没有它失败率翻倍 |
| `typeWindowsChanged` | 多窗口 / 分屏 / 弹层场景 |
| `flagReportViewIds` | **必须**。没有它拿不到 `viewIdResourceName`，依赖 id 的规则会**静默失效**，极难排查 |
| `flagRetrieveInteractiveWindows` | Android 11+ 多窗口下才能拿到正确的窗口节点 |
| `flagIncludeNotImportantViews` | 有些广告按钮被标成「非重要视图」，不加就看不见 |
| `canRetrieveWindowContent` | 不加连节点树都拿不到 |
| `canPerformGestures` | `dispatchGesture` 需要它，这是点击兜底的前提 |
| `notificationTimeout=100` | 框架层节流，100ms 内的同类事件合并。**这是第一道也是最省电的一道限流** |
| `packageNames` **留空** | 留空 = 监听全部应用。填了就只监听列出的，跳广告功能直接废掉 |

### 5.2 线程模型 —— 最容易写错的地方

```
主线程（系统回调线程）
   onAccessibilityEvent  ← 必须 1ms 内返回，只做包名/类型过滤后 post
        │
        ▼
skip-worker（HandlerThread，单线程串行）
   evaluate → SkipEngine.onWindow → NodeTreeWalker.walk → 点击
```

**为什么必须切线程**：遍历一个节点树要读几百次 IPC —— 每次 `getChild(i)` 都是一次 binder 调用。
在 `onAccessibilityEvent` 里直接做，中低端机上必然掉帧甚至 ANR。

**为什么用单线程串行**：保证同一时刻只有一个匹配在跑，引擎内部就不需要任何锁。
复杂度从「并发安全」降到「顺序执行」，这是极大的简化。

### 5.3 事件节流的两条路径

这是个反直觉的点，写错会导致「广告倒计时一直在走，规则就是不点」：

| 路径 | 语义 | 用途 |
|---|---|---|
| `debounce()` | 可合并、可被后续事件推迟 | 事件驱动。抖动风暴只跑最后一次 |
| `schedule()` | **到点必执行，不被后续事件推迟** | 引擎驱动的重试 |

如果一个 App 的开屏页 2 秒内不停刷 `contentChanged`（倒计时就会这样），
用 debounce 语义做重试会永远被推后，回调永不执行。

代码：`a11y/RetryScheduler.kt`。

### 5.4 节点遍历的三个优化

`a11y/NodeTreeWalker.kt`，BFS 遍历，三个关键剪枝：

| 优化 | 效果 |
|---|---|
| `isVisibleToUser == false` 整棵子树剪掉 | 开屏页大量 View 是 GONE 的，砍掉约一半节点 |
| 只给「有文本 / 有描述 / 有 viewId」的节点建快照 | 1200 → 约 150 个对象，**减少 80% 分配**，GC 压力肉眼可见下降 |
| 节点数上限 1200 + 深度上限 26 | 防止个别 App 把遍历拖成秒级 |

代价：只靠 `className` 匹配的规则会失效。这个取舍是明确的 —— 开屏场景里几乎没有
只靠类名就能锁定的按钮。

**1.1.0 加了 `keepStructural` 开关**：剪掉纯容器节点会把树剪断，
而 GKD 的关系选择器（`A > B`、`A + B`）要靠树结构定位。
所以遍历器多一个参数 —— 只有「当前包有 GKD 规则」时才保留完整树，
其余 App 的遍历开销一分不涨（1200 → 150 个对象的剪枝照旧生效）。

判断逻辑在服务侧：

```kotlin
private fun needsStructuralTree(pkg: String): Boolean =
    rules.currentIndex().candidates(pkg).any { rule ->
        rule.steps.any { it.isGkd } &&
            rule.packages.any { p ->
                p != "*" && (p == pkg || (p.endsWith(".*") && pkg.startsWith(p.dropLast(1))))
            }
    }
```

注意排除了 `packages = ["*"]` 的全局规则 —— 它们用的是简单选择器，
不值得让所有 App 都背上完整树的遍历开销。

### 5.5 节点生命周期的坑

Android 11 及以前，`AccessibilityNodeInfo` 是**池化**的。拿到的节点不还回去，
会导致后续 `getChild` 返回 null（节点池耗尽），表现是「规则一开始好用，用一会儿就跳不过了」。

这类 bug 极难排查，所以本项目把生命周期在类型上强制管理：

```kotlin
internal class A11yTree(
    val nodes: List<NodeSnapshot>,
    private val owned: List<AccessibilityNodeInfo>,
) : AutoCloseable {
    override fun close() { owned.forEach { A11yNodeHandle.recycleQuietly(it) } }
}
```

服务侧用 try/finally 语义包住：

```kotlin
val decision = engine.onWindow(...) { ...tree.nodes }
activeTree?.close()
activeTree = null
```

`recycle()` 在 API 33 已废弃且是空操作，所以只在 `SDK_INT < 33` 时调用。

### 5.6 点击动作的降级链

```
CLICK_NODE  → performAction(ACTION_CLICK) 失败 → dispatchGesture 点中心
CLICK_CENTER → 直接 dispatchGesture
CLICK_PARENT → 找可点击祖先 performAction，失败 → dispatchGesture
BACK        → performGlobalAction(GLOBAL_ACTION_BACK)
```

**为什么一定要有降级**：`performAction(ACTION_CLICK)` 返回 `true` 只代表「事件被投递了」，
不代表 App 真的处理了。很多自定义 View 没实现 `performClick()`，返回 true 但界面纹丝不动。
这是无障碍自动化里最经典的假阳性。

`dispatchGesture` 的手势时长设 45ms：足够被识别为点击，又不会触发长按。

### 5.7 后台保活

先说结论：**无障碍服务不需要额外保活**。

它是系统 `bindService` 起来的长生命周期服务，优先级高于普通后台进程，普通清理杀不掉。
所有「双进程互拉」「1px 前台 Activity」「播放无声音频」这类黑产手段，本项目**明确不做**
—— 它们违反系统设计意图，且在当前 ROM 上效果也越来越差。

真正有效的只有三件事，全是引导用户手动操作：

| 措施 | 生效条件 |
|---|---|
| 加入电池优化白名单 | `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，部分 ROM 改写这个对话框 |
| 允许自启动 | 各家 ROM 的「自启动管理」，无统一 API |
| 省电策略设为「无限制」 | 小米 / 华为 / OPPO / vivo 都在这条上杀得最狠 |
| 任务列表加锁 | 一加 / OPPO 系特有，用户从最近任务卡片下拉加锁 |

代码里 `A11yUtils.isIgnoringBatteryOptimizations()` + `requestIgnoreBatteryOptimizations()`
只做检测和引导，不做任何对抗性保活。

另外 `WorkManager` 每 12 小时跑一次规则更新。这里用 WorkManager 而不是 `AlarmManager` 的原因：
不需要精确时刻、系统会批量调度更省电、不用申请 `SCHEDULE_EXACT_ALARM`（Android 12+ 那个权限很麻烦）。

## 6. 与 GKD、李跳跳的借鉴与差异

### 6.1 三方对比

| 维度 | GKD | 李跳跳 | 本项目 SplashSkip |
|---|---|---|---|
| 开源 | **开源，GPLv3** | **闭源**（仅有社区逆向的规则包） | 开源 |
| 最低版本 | Android 7.0（API 24） | 较低（未公开） | Android 8.0（API 26） |
| 提权方式 | 无障碍 + **Shizuku**（免无障碍点击） | 仅无障碍 | 无障碍 + **Shizuku（可选）** |
| 规则语言 | CSS 式 AST 选择器：父子/兄弟关系、布尔表达式、取反、表达式运算 | 内置文本/ID 表 + 坐标兜底 | **两套并存**：原生扁平 Selector + **完整 GKD AST 选择器** |
| 规则格式 | JSON5 | 内置 + 后期支持导入 | **原生 JSON + GKD JSON5 都能加**（按内容自动识别） |
| 规则分发 | 多订阅 + `updateUrl` / `checkUpdateUrl` 增量检查 + 分类分组 | **内置，靠发版** | **GKD 订阅** + 版本号 + 版本回退保护（无验签，GKD 生态无签名体系） |
| 签名校验 | 无 | 无 | **有（强制）** |
| 调试能力 | 强：快照审查（悬浮窗/音量键/快捷开关/Web 工具四种抓取）+ 浏览器审查 | 无 | 命中日志 + **节点树快照导出**（延时抓取 + 树形查看） |
| 性能手段 | `fastQuery` / `matchRoot` / `activityIds` 作用域 / `actionCd` 冷却 | 定时轮询为主 | Activity 作用域 + 包名倒排索引 + 事件双路径节流 + 节点剪枝 |
| 误点防护 | 靠选择器精度（规则作者责任） | 靠内置白名单 | **运行时护栏**（面积/黑名单/禁用态/严格模式） |
| 定位 | 通用 UI 自动化平台 | 极简开屏跳过 | 窄场景、重护栏的开屏跳过 |
| 现状 | 活跃维护，41k+ star | 2023-08 停更，后由第三方接手至 v2.7.1 | 本设计 |

### 6.2 借鉴了什么

| 借鉴点 | 出处 | 本项目做法 |
|---|---|---|
| 规则与引擎分离 | GKD | 完全一致。规则是外部 JSON，引擎只认数据结构 |
| `checkUpdateUrl` 增量探测 | GKD | 一致。先拉版本号，没变就不下全量 |
| Activity 作用域（`activityIds`） | GKD | 一致。避免在用户正常浏览时反复遍历节点树 |
| 冷却 / 触发次数上限（`actionCd` / `actionMaximum`） | GKD | 一致。`actionCooldownMs` + `maxTriggers` |
| 触发延迟（`matchDelay`） | GKD | 一致。`matchDelayMs` |
| 规则分组与优先级 | GKD | 用 `priority` 单字段表达，简化了 |
| 「跳过而非屏蔽」的产品定位 | 李跳跳 | 一致。这是法律上的关键区分 |
| 零配置即可用 | 李跳跳 | **不一致**。本项目不内置任何规则，首次使用必须自己添加订阅源 |
| 轻量（李跳跳 2MB） | 李跳跳 | 无第三方 SDK，无图片资源，无 OpenCV |

### 6.3 差异在哪 —— 四个明确的不同

**差异一：规则验签（GKD 没有，本项目强制）**

> **1.2.0 已随自研格式一起移除**，理由见上文引用块的说明。以下保留为决策记录。

GKD 的多订阅生态靠社区自律。本项目人少规则少，只能靠密码学：
所有远程规则必须 ECDSA 验签，拿不到 `.sig` 或验签失败一律拒收。
代价是发布规则多一步签名，收益是彻底堵掉「规则投毒」这个攻击面。

> **GKD 格式是唯一的例外**：GKD 社区本来就没有签名体系，对它强制验签等于直接拒收这个源。
> 所以识别为 GKD 格式时自动按「未验签」加载，订阅列表里明确标注「GKD 格式　未验签」。
> 这是安全性上的让步 —— 用户是主动添加这个源的，风险自己承担。

**差异二：运行时护栏（GKD 靠选择器精度）**

GKD 把精度责任交给规则作者；本项目在点击前再加五道运行时检查（面积/黑名单/禁用态等）。
这个差异源于生态规模：GKD 有 1300+ 条经过验证的规则和社区审核，
本项目规则少、没有审核，必须在运行时兜底。**宁可漏跳，不可误点。**

> **1.1.0 起对 GKD 规则例外**：GKD 规则精确到具体节点（连父子兄弟关系都写明了），
> 再套「右上角区域 + 短文本」这套启发式护栏只会误杀真规则 ——
> 实测真实 GKD 订阅里大量规则命中的是屏幕中下部的小图标。
> 所以护栏只作用于本项目原生格式的规则，GKD 规则直连。
> 风险由规则作者和用户自己承担，界面上的「未验签」标注就是提示。

**差异三：Shizuku 作为「可选增强」而非「默认依赖」**

Shizuku 能让 App 以 shell 身份直调系统命令，绕过无障碍的事件分发，延迟从 100~200ms 降到接近 0，
而且不依赖无障碍服务常驻（更省电）。

GKD 把它当主推通道。本项目把它做成**可选**，三档切换（自动 / 仅无障碍 / 仅 Shizuku），默认 AUTO：

| 场景 | 行为 |
|---|---|
| 用户没装 Shizuku | 走无障碍，功能完整可用 |
| 用户装了并授权 | AUTO 自动切到 Shizuku，延迟更低 |
| 某个 App 用 Shizuku 点不动 | 可在设置里强制切回无障碍 |

理由：Shizuku 要求用户额外装 App、每次重启后重新授权、部分 ROM 还有兼容问题。
把它设成必需会让大多数用户卡在第一步。做成可选，愿意折腾的人能拿到更低延迟，
不愿意的人开箱即用。

实现上有个值得记的坑：`Shizuku.newProcess()` 在 API 13.x 里被标成了 private（不是公开 API），
只能反射调用。反射失败会静默降级回无障碍 —— 不能因为 Shizuku 不给用就整个不工作。
proguard 里必须 keep `rikka.shizuku.Shizuku` 的成员名，否则 release 包反射必挂。

**差异四：选择器两套并存（GKD 树形 + 本项目扁平）**

GKD 的 CSS 式 AST 选择器支持：

```
@TextView[text*='跳过'] < [vid='container'] > [index=2]
```

这种「锚点 + 相对路径」的写法抗改版能力极强 —— App 把按钮文案改了，只要容器 id 没变，规则还能用。

1.0.0 时的做法是用「文本 + 区域 + 尺寸 + 类名」四把锁替代，表达力弱一档。
**1.1.0 起这套替代方案不再是唯一选择**：原生格式保留，GKD 的树形选择器整套搬了过来（见 6.4）。

### 6.4 GKD 兼容层：怎么把 GKD 订阅接进来

这是 1.1.0 最大的增量。难点不在「读个 JSON」，而在 GKD 的选择器是**图查询**语义 ——
它要在无障碍节点树上按父子/兄弟关系求值，而本项目原生的规则是**扁平单节点**匹配。
两套不是同一个物种，硬塞进同一套模型会把引擎搞复杂。

所以做的是**格式适配 + 引擎双路径**：

```
GKD 订阅(JSON5)
   │
   ├─ Json5.parse          手写 JSON5 解析器（无引号 key / 单引号 / 尾随逗号 / 注释）
   │                       Gson 的宽松模式救不了这些
   │
   ├─ GkdCodec             apps[].groups[].rules[] → 本项目的 AppRule/Step
   │                       Step.gkd 里装解析好的选择器 AST
   │
   ├─ GkdSelectorParser    选择器字符串 → AST（属性表达式 / 逻辑 / 关系算符）
   │
   └─ GkdMatcher           在结构化节点树上求值
```

#### 选择器语义里最容易搞反的地方

GKD 的关系算符**与 CSS 直觉相反**，而且匹配是**从右往左**做的。官方定义：

| 算符 | 官方含义 | 从右往左回溯时 |
|---|---|---|
| `A > B` | A 是 B 的**祖先** | 从 B 往上找 |
| `A < B` | A 是 B 的**直接子节点** | 从 B 往下找 |
| `A + B` | A 是 B 的**前置兄弟** | 从 B 往前找 |
| `A - B` | A 是 B 的**后置兄弟** | 从 B 往后找 |
| `A << B` | A 是 B 的**子孙** | 在 B 的子树里找 |

记错方向的后果不是报错，而是**静默地一条都不命中**。

另外两个反直觉的点：

- **`A >n B` 里的 n 是「任意正整数」**，意思是任意深度的后代，不是「第 n 层」。
- **目标节点默认是链尾**（最右的那个属性选择器），`@` 才会改写目标。
  `@LinearLayout > [text="跳过"]` 点的是 LinearLayout，不是「跳过」。

#### 节点树必须结构化

原生的 `NodeSnapshot` 只是个扁平列表，只有 `depth` 没有父子指针 ——
这在扁平匹配下够用，但关系选择器需要知道「谁是谁的爹」。

而且遍历器原本会**剪掉无文本/描述/viewId 的纯容器节点**（省 80% 对象分配），
这会把树剪断，`>` 的语义随之失真。

改法：`NodeSnapshot` 加了 `parentIndex` / `childIndices` / `indexInParent` /
`dfsOrder` / `childCount` 五个运行时索引（放在 body 里，不参与 data class 的 equals），
遍历器加 `keepStructural` 开关 —— 只有「当前包有 GKD 规则」时才保留完整树，
其余 App 的遍历开销一分不涨。

#### 全量解析 + 分类开关（1.3.0 起）

真实 GKD 订阅（`Lin-arm/GKD_subscription` v620）有 3880 条规则、992 个 App、
2477 个规则组。1.2.x 早期只导「开屏」分类（283 条 / 176 个 App），理由是
「更新提示、青少年模式这类弹窗可能是用户想看的」。

这个取舍在实际使用里被推翻了：用户拿着 App 去和 GKD 对数，看到的是
「998 应用 / 2473 规则 vs 177 应用 / 283 规则」，第一反应是解析坏了。
所以 1.3.0 先改成无脑全量导入 —— 结果**第二天就挨骂**：非开屏分类
（局部广告、功能类、更新提示）在用户正常刷信息流、点设置的时候自动动手。

现在是第三条路：**全量解析，按分类执行**。

- **解析全量**：`apps[].groups[]` 与 `globalGroups[]` 全部进内存，UI 显示
  「已解析 3864 条 / 986 个应用」，数字和 GKD 对得上，谁也不会觉得规则丢了。
- **执行按分类过滤**：`RuleIndex` 只装勾选分类的规则。分类来自 GKD 顶层的
  `categories: [{key, name, enable}]`，group 靠「分组名以分类名开头」的约定
  归属（实测 2477 个分组 100% 匹配）。默认值直接取订阅作者的 `enable: true`
  —— Lin-arm 订阅里只有「开屏广告」，等于复刻 GKD 的默认行为。
- **订阅页有分类开关**：11 个分类逐条列出规则数和开关，用户想开「更新提示」
  自己去开，开关持久化在 `splashskip.categories`。
- **开屏分类 priority = 100**，其它分类 0。引擎按 priority 降序遍历，
  开屏页上先试「跳过」，不会先撞上「关闭广告」。
- **一个 App 多条规则**：`RuleResolver.resolveAll` 返回全部适用规则，
  `Session` 持有一组规则，逐条尝试。1.2.x 只取一条。

实测数字（Lin-arm v620）：已解析 3864 条 → 默认生效 **294 条**（开屏广告），
打开「更新提示」后变 557 条，关掉回到 294，重启后保持。

解析损耗：4115 条选择器里 13 条失败（0.32%），几乎都是 `->` 算符
（要求记住查询路径，当前的从右往左回溯模型表达不了）。这些规则被跳过
并在订阅页列出告警，不影响其余。

启动开销：解析 1.3MB JSON5 + 4115 条选择器约 214ms（桌面 JVM），
手机上 400~800ms。所以 `RuleRepository` 初始化只建目录，解析丢到
`rules-loader` 线程，完成后原子替换 volatile 快照并回调 UI ——
主线程零阻塞。

#### GKD 订阅没有签名

GKD 社区本来就没有签名体系，对它强制验签等于直接拒收。
所以识别为 GKD 格式时自动按「未验签」加载，订阅列表里明确标注。
这是安全性上的让步，不是疏漏 —— 用户是主动添加这个源的。

### 7.1.1 UI 结构的两个决定

**一、底部 4 个 tab，按「用户意图」而不是「技术模块」划分。**

参考 GKD 的信息架构：

| tab | 回答的问题 |
|---|---|
| 首页 | 现在是什么状态？服务开着吗？规则几条？ |
| 订阅 | 规则从哪来？有多少？什么时候更新的？ |
| 应用 | 哪个 App 我单独调过？ |
| 设置 | 权限怎么给？数据在哪？版本多少？ |

首页刻意克制，只放状态和两个高频动作（抓快照、看日志）。所有低频且带副作用的入口
（权限跳转、数据清理、快照管理）都收进设置页。

**二、Fragment 用 hide/show，不用 replace。**

`replace` 会销毁上一个页面，切回来时滚动位置、列表状态全丢。`hide/show` 保留所有页面的
View 状态，代价是 4 个页面同时占内存 —— 对这种配置型 App 完全可以接受。

**三、安全区域必须在根布局统一处理。**

`targetSdk 35` 在 Android 15 上会**强制 edge-to-edge**，内容默认绘制到状态栏和导航栏下面。
不处理 inset 的话，页面顶部文字会直接跟状态栏的时钟、电量图标重叠。

处理方式见 `MainActivity.applyWindowInsets()`：

```kotlin
val bars = insets.getInsets(systemBars() or displayCutout())
root.setPadding(bars.left, bars.top, bars.right, 0)   // 顶部交给根布局
bottomNav.updatePadding(bottom = bars.bottom)         // 底部交给导航栏自己吃
```

底部为什么单独处理：让 `BottomNavigationView` 的白色背景延伸到系统导航条后面，
避免出现「导航栏白色 + 下面一截灰色」的色块接缝。

实测数据（1080×2400 模拟器）：状态栏高 128px，改之前顶部提示条 bounds 是 `[0,0][1080,147]`
（直接压在状态栏上），改之后是 `[0,128][1080,275]`。

**四、视觉风格：iOS 柔光玻璃（glassmorphism）。**

Android 上做「毛玻璃」有三条路：

| 方案 | 问题 |
|---|---|
| `RenderEffect` 真模糊（API 31+） | 要抓下层内容渲染成 Bitmap 再 blur，实现复杂，低版本没有 |
| `Window.setBackgroundBlurRadius` | 只能模糊**窗口外**的内容，对 App 内的卡片无效 |
| **半透明 + 受光高光 + 彩色光斑背景** | 靠视觉层次，成本低一个数量级 |

选第三条，但**第一版做错了**，值得记下来：

> 第一版背景是一片均匀的浅渐变，卡片设 82% 白 + 白色描边。
> 结果卡片透出来是均匀色，看起来就是一块**灰板**，完全没有玻璃感。
>
> 根因：**玻璃感来自「透过玻璃看到背后的色彩层次」，不是来自「半透明」本身。**
> 背景没有色彩变化时，降低不透明度只会让卡片变灰，不会变透。

修正后的三层结构：

| 层 | 值 | 作用 |
|---|---|---|
| 背景光斑 | 4 个径向渐变（蓝 `#B3A8C6FF` / 紫 `#ADBC9CFF` / 粉 `#ADFFA0C8` / 青 `#9982E0D8`），半径 360~440dp | **这是玻璃感的唯一来源**。光斑边缘天然柔和，卡片透过去就是「毛玻璃背后有模糊色块」 |
| 卡片底 | `#8CFFFFFF`（55% 白） | 留 45% 透明让光斑透上来，卡片颜色随位置变化 |
| 顶部受光 | 线性渐变 `#4DFFFFFF` → 透明，内缩 1dp | 模拟玻璃上沿反光。**这是「玻璃」和「半透明塑料片」的分界**，没有它卡片显得廉价 |

关于「真模糊」的一个技术事实：**模糊对纯渐变背景是零收益的** —— 渐变模糊后还是渐变。
iOS 的毛玻璃之所以明显，是因为它背后有照片、图标这类高频内容。
本项目背景只有光斑（本身已是柔和渐变），所以没有引入 `RenderEffect` 的必要。

两个容易踩的点：

1. **不要用 `elevation` 做阴影**。Android 的 elevation 阴影是硬投影、边缘无过渡，
   在半透明卡片上会形成一圈明显的灰色硬边 —— 这正是「灰白过渡生硬」的元凶。
   玻璃质感靠透明度、受光和色彩层次，不靠阴影。第一版就是被这个坑了。
2. **按钮要用 `AppCompatButton` 而不是 `Button`**。Material3 主题下 `Button` 会被自动替换成
   `MaterialButton`，而 `MaterialButton` 会忽略 `background` 属性，自定义圆角直接失效。

**五、应用页：搜索 + Switch + 批量。**

三个交互各管一件事，避免互相抢戏：

| 控件 | 作用 | 为什么这么设计 |
|---|---|---|
| 搜索框 | 按应用名 / 包名实时过滤 | 装了几十个应用时滚动找太慢，包名匹配方便按厂商前缀筛 |
| **Switch** | 启用 / 禁用 | 最高频操作（某个 App 误点了赶紧关掉）必须一步到位，不能藏菜单里 |
| 点整行 | 三态选择：自动 / 学习 / 禁用 | 学习模式不是二态，Switch 表达不了，放这里做精细设置 |
| 批量 | 多选后一次性设置 | 「除了微信支付宝全都不管」这类场景 |

实现上是在 `SimpleAdapter` 里加了两种互斥的可选控件（`selectable` 显示复选框、`showSwitch` 显示开关），
而不是为应用页单写一套 adapter：两者默认都 `GONE`，所以规则列表、日志列表共用同一个适配器完全不受影响。

**Switch 有一个必须处理的坑**：RecyclerView 复用 ViewHolder 时，
直接 `setChecked()` 会触发上一个 item 残留的监听器，导致写错数据。
必须先解绑再设状态：

```kotlin
holder.switchView.setOnCheckedChangeListener(null)
holder.switchView.isChecked = item.checked
holder.switchView.setOnCheckedChangeListener { _, checked -> onSwitchChanged(item, checked) }
```

另一个坑：**`onClick` 必须是构造函数的最后一个参数**。
调用方普遍写成 `SimpleAdapter(items) { item -> ... }` 的尾随 lambda 形式，
而 Kotlin 的尾随 lambda 只绑定最后一个参数 —— 加参数时如果把 `selectable` 放在 `onClick` 后面，
所有调用点会静默变成「lambda 传给了 selectable」，编译直接报类型不匹配。

**为什么把 `core` 做成零 android 依赖？**

不是为了「纯粹」，是为了**能测**。引擎里有大量边界判断（超时、冷却、尝试次数、护栏拦截），
这些用 Robolectric 测一次要几秒，用纯 JVM 测一次几十毫秒。一个测试套件跑 3 秒还是 3 分钟，
决定了你愿不愿意在改代码之后跑一遍。

### 7.2 关键数据流

```
系统无障碍事件
   │
   ▼
SplashSkipService.onAccessibilityEvent         [主线程，1ms 返回]
   │  只做：包名过滤、自身包名排除、事件类型分流
   ▼
worker.post → evaluate()                        [skip-worker 线程]
   │
   ▼
SkipEngine.onWindow(pkg, activity, screen, nodesProvider)
   │
   ├─ RuleIndex.candidates(pkg)                 [HashMap 查表]
   ├─ RuleResolver.resolve → AppRule
   ├─ Session 生命周期管理（超时/冷却/次数）
   │
   ▼ （仅在真正要匹配时才调用）
nodesProvider → NodeTreeWalker.walk(rootInActiveWindow)
   │  BFS + 剪枝 → List<NodeSnapshot> + 待回收节点
   ▼
NodeMatcher.matches(node, selector, screen)     [逐条 step 遍历]
   │
   ▼
SafetyGuard.isSafe(node, screen, strength)      [五道护栏]
   │
   ▼
EngineHost.perform(node, step)                  [点击降级链]
   │
   ▼
```

#### R8 混淆最大的风险不是崩溃，是静默失效

Gson 按字段名反射。字段名一旦被混淆成 `a`/`b`/`c`，反序列化会得到一堆 null 和 0，
表现出来是「规则加载 0 条」「订阅加不进去」「快照字段全空」——
不报错、不崩溃，只是功能悄悄没了，比崩溃难查得多。

**但只 keep 字段名还不够。** 这是 1.1.0 实测踩到的坑：

```proguard
-keepclassmembers class com.splashskip.rules.RuleCodec$* { <fields>; }   # ❌ 不够
```

`-keepclassmembers` 只保住字段名，**类本身照旧被 R8 处理**。
`RuleCodec$SelectorDto` 这种 DTO 只被 Gson 反射 new、没有直接实例化点，
R8 认为它「无人使用」→ **把它抽象化**（移除构造函数）。
Gson 拿到一个抽象类就直接抛：

```
Abstract classes can't be instantiated! Adjust the R8 configuration
or register an InstanceCreator or a TypeAdapter for this type.
```

后果是**整份订阅解析失败**，规则数为 0 —— 而且 **debug 包完全正常**，
只测 debug 会完全错过这个 bug。

正确写法是保留整个类：

```proguard
-keep class com.splashskip.rules.RuleCodec$* { *; }
```

需要 keep 的类：

| 类 | 用途 |
|---|---|
| `rules.RuleCodec$*` | 规则 JSON 传输层 DTO（订阅、手写规则） |
| `rules.SubscriptionEntry` | 订阅配置（存 SharedPreferences） |
| `core.model.**` | 规则模型 |
| `core.engine.HitRecord` | 命中日志 JSONL |
| `a11y.SnapshotDoc` / `SnapshotNode` | 界面快照 JSON |
| `core.gkd.**` | GKD 选择器 AST（不反射，但结构要能被人看懂） |

**验证 keep 规则真的生效**：release 包 `debuggable=false`，`run-as` 用不了，
但模拟器可以 `adb root` 直接写文件。

往 `files/rules/remote/` 放一份订阅文件（文件名与内容里的 `id` 一致），
重启服务后看日志：

```
I RuleCodec: 解析完成：规则=283 致命=无 告警=19
I SplashSkipService: 无障碍服务已连接，规则 283 条
```

- 规则数对得上 → keep 规则生效
- 报 `Abstract classes can't be instantiated` → 少 keep 了某个 DTO
- 规则数是 0 → 解析失败，看 `RuleCodec` 的异常日志

**别只在 debug 包上测这一项。** debug 不混淆，R8 的所有坑都测不出来。

```bash

# 产物：app/build/outputs/apk/release/app-release.apk
```

## 8. 使用与调试

### 8.1 上手流程

```
1. 安装 → 打开 App
2. 点「去开启无障碍服务」→ 系统设置里找到「SplashSkip」→ 开启
   （Android 12+ 若提示「受限制的设置」，先去「应用信息 → 允许受限制的设置」）
3. 回到 App，状态显示「已开启」
4. 去「订阅」页点「＋ 添加订阅」填一个规则订阅 URL（应用不内置规则，这步必须做）
   · GKD 格式的订阅（如 gkd.json5）直接填 URL 即可，会自动识别
5. 打开任意带开屏广告的 App 验证
6. 没跳过？去「命中日志」看有没有记录
```

### 8.2 排查「为什么没跳过」

按这个顺序查，能覆盖 95% 的问题：

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志有「被安全护栏拦截」 | 面积/黑名单/禁用态触发 | 看具体原因；确认是误拦就调整规则或提强度 |
| 日志有「会话超时」 | 按钮出现太晚 | 加大 `timeoutMs` / `matchDelayMs` |
| 日志有「已达尝试上限」 | 重试次数不够 | 加大 `maxTriggers`，或把 `retryDelaysMs` 拉长 |
| 日志里**完全没记录** | 规则没命中包名/Activity | 核对包名，把 `activities` 清空试试（代价是耗电） |
| 日志有命中但界面没动 | `performAction` 假成功 | 把 action 改成 `CLICK_CENTER` 走手势 |
| 订阅页有「解析告警」 | 这条规则的选择器解析不了 | 看告警内容；GKD 规则可能是用了暂不支持的语法 |

**GKD 规则的额外排查点**：

| 现象 | 原因 | 处理 |
|---|---|---|
| 规则加载 0 条，日志报 `Abstract classes can't be instantiated` | R8 把 DTO 抽象化了 | 补 proguard keep 规则，见 7.5 |
| 规则数比预期少几条 | GKD 的 rule key 撞 id，被合并去重 | 已自动加 `#2` 后缀修复，订阅页会列告警 |
| 某条规则始终不命中 | GKD 选择器方向理解反了 | 见 6.4 的算符对照表；用「抓快照」看节点树的实际层级 |
| GKD 规则加载后没生效 | 目标 App 不在 `packages` 里 | GKD 的 `activityIds` 是相对类名，本项目按后缀匹配 |

### 8.3 写一条新规则

```json
{
  "id": "com.example.app.splash",
  "name": "示例 App 开屏",
  "packages": ["com.example.app"],
  "activities": [".*Splash.*"],
  "priority": 100,
  "timeoutMs": 3000,
  "steps": [
    {
      "selector": {
        "text": ["跳过", "跳过广告"],
        "textMode": "PREFIX",
        "region": [0.55, 0, 1, 0.18],
        "maxTextLength": 10
      },
      "action": "CLICK_NODE"
    }
  ]
}
```

写规则的实际手法：先用宽松条件（`CONTAINS` + `region: [0,0,1,1]`）让规则命中，
在日志里看到「命中 xxx」之后，再逐步收紧条件（改 PREFIX、加区域、加长度上限），
直到只有目标按钮能命中。反过来做 —— 一上来就写严格条件 —— 你连它为什么不命中都不知道。

### 9.1 快照导出的实现说明

设计上有两个关键决定：

**一、完整树和匹配树走两条路径。**

`NodeTreeWalker` 为匹配服务，会剪掉「无文本、无 id」的容器节点，把 1200 个节点压到 150 个左右。
但写规则时最需要看的恰恰是那些容器 —— 「跳过按钮挂在哪个 FrameLayout 下面」决定了规则的抗改版能力。
所以 `RawTreeDumper` 走另一条路：不剪枝，保留完整层级，只做节点数（3000）和深度（40）的硬上限，
超了就标 `truncated = true`，而不是静默丢数据。

**二、延时抓取，而不是立即抓取。**

用户点「抓取快照」时 App 还在前台，此刻抓到的只会是自己的界面。
所以设计成点完按钮给 5 秒，让用户切到目标 App，再抓 `rootInActiveWindow`。
倒计时和抓取都在无障碍服务的 `skip-worker` 线程上跑，回调切回主线程 —— 这样即使
MainActivity 被系统回收也不影响抓取结果。

抓到的 JSON 存 `filesDir/snapshots/<pkg>_<时间>.json`，明文格式（方便拷到电脑上 grep），
最多保留 50 份。App 内的查看页用缩进文本渲染，比直接看 JSON 直观得多。
